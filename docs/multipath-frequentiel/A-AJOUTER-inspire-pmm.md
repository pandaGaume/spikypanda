# Ce qu'on ajoute, inspiré de `predictive-maintenance-mcp` (analyse du code)

*Analyse en lecture du code réel de [predictive-maintenance-mcp](https://github.com/LGDiMaggio/predictive-maintenance-mcp)
(7 sous-systèmes, ~727k tokens lus). Rappel du cadrage : eux = **assistant LLM sur hôte, DSP classique** ;
nous = **substrat appris, embarqué, streaming, µW**. On adopte leurs bonnes pratiques, on devient
compatible, on comble les trous, on garde notre avantage. Complète [`PILE-MONITORING-DYNAMIQUE.md`](PILE-MONITORING-DYNAMIQUE.md).*

## Priorité (le shortlist si on ne fait que 5 choses)

1. **Refus typé + provenance + unités** (bonnes pratiques ci-dessous) : quasi gratuit, gros gain de crédibilité, sert directement le papier MCSA et motorwatch.
2. ✅ **FAIT — Nœud sévérité ISO 20816-3** (trou #2) : `plugin-iso` (`ISO.Severity:iso20816`), lit le tag d'unité, refuse si absent, intègre accel→vitesse, classe en zone A/B/C/D avec provenance. 14 tests verts (oracles analytiques + refus). Alarme *ancrée sur un standard* à côté du score appris.
3. **Compatibilité MCP** (vocabulaire d'outils + `signal_id` + schémas de résultat) : rend notre stack pilotable par les mêmes clients LLM que les leurs.
4. **Couche RUL** (trou #1) : un Kalman 2 états sur la dérive inter-session, avec leur garde « pas d'extrapolation sur une mesure ». C'est notre plus gros trou.
5. **Baseline DSP classique comme oracle** (trou #7) : FFT+envelope+BPFO + OneClassSVM/PCA, pour avoir le chiffre « on bat la détection de nouveauté classique » à côté du 88% BRB. Débloque aussi le papier.

## 1. Bonnes pratiques à adopter (leur vraie valeur : la discipline, pas la math)

Toutes tirées du code ; classées par effort.

| **bas** | **Snapshots golden avant refacto** : figer les sorties byte-level sur fixtures avant de toucher l'abaissement LRU→biquad ou un serializer ; distinguer défaut vs explicite pour rester byte-identique. | Leur pire classe de bug = drift de valeur. Un hôte LLM ne peut pas perdre le caveat s'il est dans une union typée ; un bloc peut refuser pendant que les autres tournent. |

## 2. Trous à combler (ce qu'ils ont, qu'on n'a pas)

- [ ] **RUL / extrapolation de vie** (on n'a **rien**). Ajouter un **Kalman 2 états** `état=[niveau, taux]`, `F=[[1,dt],[0,1]]`, `H=[1,0]`, `Q=q·[[dt³/3,dt²/2],[dt²/2,dt]]` sur la série de dérive **inter-session** (2×2, MCU-cheap). Reprendre leur variance delta-method **avec le terme de covariance croisée `P[0,1]`**. Garde stricte : **RUL exige N≥3 mesures inter-session** sur du temps réel écoulé ; typer l'analyse intra-fenêtre streaming comme `SCREENING`, jamais pronostic. Aussi : fits linéaire et log-linéaire (`fit_r_squared` labellisé *goodness-of-fit, PAS confiance*), warning « Nx au-delà de l'horizon observé », précondition d'espacement uniforme (refuser si spread>10%).
- [x] ✅ **FAIT + INTÉGRÉ ÉDITEUR — Sévérité ISO 20816-3 (RMS vitesse)** : `plugin-iso` / `ISO.Severity:iso20816` (`packages/dev/plugins/iso/src/severity/iso20816.ts` + `.node.ts`). Table `ZONE_BOUNDARIES` exacte, bande 10-1000 Hz (bord bas 2 Hz sous 600 rpm), accel→vitesse par intégration fréquentielle FFT `V(f)=A(f)/(j·2πf)` (via `getFFTEngine`, g=9.80665, DC skippé), `classifyZone` avec `≤`, plancher 15 kW, refus fs<~2106 Hz, **lit le tag d'unité et refuse si absent**. Tests : `packages/tests/iso/iso20816.test.ts`, 14 verts. **Bundlé (webpack) + déployé + enregistré dans l'éditeur** (script tag + `load("SpkPluginIso","iso")` ; vérifié live : `__nev2.nodes` = 183 types dont `ISO.Severity:iso20816`, `assess()` runtime = oracle + refus). *NB : intégration fréquentielle plutôt que Butterworth SOS, équivalent pour une RMS large-bande. Le core a dû être rebundlé (nouveau `resolveUnit`) → tous les bundles éditeur rebundlés pour cohérence.*
- [ ] **Envelope-demod (bandes roulement)**. Nœud qui **réutilise notre LRU abaissé en biquads** comme étage passe-bande 500 Hz→min(5000, Nyquist-1), puis `|analytic|`, puis le fix U9, puis `find_peaks(prominence=2 dB, distance ~1 Hz)`. Complète MCSA, donne un canal de corroboration classique.
- [ ] **Fréquences caractéristiques + catalogue vérifié**. Nœud analytique (Randall & Antoni 2011) : `BPFO=(Z/2)f_s(1-r cosα)`, `BPFI=(Z/2)f_s(1+r cosα)`, `BSF=(Pd/2Bd)f_s(1-(r cosα)²)`, `FTF=(f_s/2)(1-r cosα)`, `r=Bd/Pd`, alimenté par le rpm du **scheduler RS-385** pour **tuner/gater nos résonateurs appris**. + catalogue JSON avec **source obligatoire par entrée** (leur v2.0 a *supprimé* ~20 entrées à géométrie fabriquée). Oracle unit-test : CWRU 6205 BPFO=3.5848x. *Note : leur BSF = spin de bille (1x), pas le 2x défaut-bille.*
- [ ] **Génération de rapport**. Module motorwatch : HTML autonome avec bloc JSON de métadonnées embarqué + `.docx` optionnel (stats, top pics, matches de fréquences, chart zone ISO, diagnostic libre), noms horodatés + compteur monotone. **CRITIQUE : inliner le runtime du chart ou rendre du SVG statique** (leur HTML tire Plotly d'un CDN → casse en air-gapped, contraire à notre éthos offline/edge).
- [ ] **RAG sur manuels + ingestion PDF**. RAG TS/in-browser : démarrer par le chemin **TF-IDF sans dépendance** (ngrams (1,2), sublinear_tf, cosinus, top_k=5, chunks paragraphes ~1024 car, cache mtime-hash), backend embeddings optionnel derrière un flag. + ingestion PDF avec **fallback OCR** (couche texte <20 car → OCR) et hints regex (désignation roulement, RPM, kW) pour **auto-configurer régime et fréquences de faute** depuis les datasheets client.
- [ ] **Baseline DSP classique = oracle de validation** (le papier MCSA en a besoin). Livrer FFT+envelope+matching BPFO (±5%, 3 harmoniques) **ET** un harness `OneClassSVM`/`LOF` + `StandardScaler` + `PCA(0.95)` entraîné sur healthy-only, pour **benchmarker notre clustering open-set appris** → chiffre honnête « on bat la nouveauté classique » à côté du 88% BRB.
- [ ] **Trend + onset statistiquement gardés** sur le canal de dérive. OLS qui ne déclare une direction que si `p-value < 0.05` (refuser à n<3), + détecteur d'onset (baseline première moitié mean/std, flag 1er échantillon > mean+3·std ; fallback `eps` si std=0). O(1) d'état, à côté de MotionWatch.
- [ ] **Scalaires DSP classiques streaming**. Les 17 features temporelles, surtout **kurtosis excès (Fisher, =0 pour gaussien)**, crest/shape/impulse/clearance, comme scalaires quasi-gratuits sur MCU **à côté** de nos embeddings (avec leurs gardes /0). Donne un canal de corroboration en *lingua franca* vibratoire.
- [ ] **Calibration semi-supervisée des seuils** depuis nos rares fautes labellisées (grille manuelle + balanced-accuracy) appliquée à nos seuils d'ancre/escalier et coupures de nouveauté, au lieu de les régler à la main.
- [ ] **Labelliser les étages par bloc ISO 13374** (1 Acquisition, 2 Manipulation/features, 3-4 State/Health, 5 Prognostics, 6 Advisory) pour que motorwatch se lise comme une chaîne PHM conforme aux standards ; notre étage capteur = « Blocs 1-3 faits à l'edge ».

## 3. Plan de compatibilité (interop MCP)

- **Enregistrer nos outils sous leurs noms exacts** pour qu'un hôte LLM pilote les deux stacks : `list_signals(scope)`, `load_signal(filepath, signal_id?, sampling_rate?, signal_unit, overwrite)`, `get_signal_info`, `generate_test_signal`, `clear_signals` ; `analyze_fft`, `analyze_envelope(filter_low=500, filter_high=5000, num_peaks)`, `analyze_statistics`, `extract_features_from_signal`, `compute_power_spectral_density`, `compute_spectrogram_stft` ; `assess_severity`, `diagnose_vibration`, `check_bearing_faults`, `calculate_bearing_characteristic_frequencies`, `search_bearing_catalog`, `train_anomaly_model`, `predict_anomalies` ; `estimate_rul`, `analyze_signal_trend` ; `generate_maintenance_recommendations`.
- **Handle `signal_id` opaque** + resolver canonique dans `@cyanmycelium/mcp-core` (load renvoie un id, tout outil aval le prend, not-found liste les ids dispo + explique l'éviction LRU).
- **Vocabulaire de faute canonique** comme clé machine-readable : `{outer_race, inner_race, ball, cage, misalignment, unbalance, looseness}` (les acronymes BPFO… y mappent). **Étendre avec `broken_rotor_bar`** pour notre MCSA dans le même style closed-vocab ; lever (pas drop) sur label inconnu.
- **Miroir de leurs contrats de résultat** en TS/JSON-schema : `SpectralPeak{frequency_hz, magnitude, magnitude_db, note}`, `EnvelopeResult`, `StatisticalResult{rms/crest/kurtosis/skewness + signal_unit}`, `VibrationSeverityResult{zone, severity_level, color_code, alert_level, boundaries, rms_velocity_mm_s, machine_group, support_type, threshold_provenance}`, `bearing_frequencies`, `fault_checks[]{expected_frequency_hz, detected, deviation_pct, harmonics_detected[], evidence_strength}`, `RULEstimationResult`, `TrendAnalysisResult`.
- **Enveloppe status en union discriminée partout** : `status + reason + remedy`.
- **Aligner les enums exactement** : `signal_unit{g,m/s2,mm/s,m/s}`, `machine_group{1,2}`, `support_type{rigid,flexible}`, zones `A/B/C/D`, `severity_level{Good,Acceptable,Unsatisfactory,Unacceptable}`, `color_code{green,yellow,orange,red}`, `alert_level{none,warning,alarm,danger}`.
- **Sidecar `{stem}_metadata.json`** (sampling_rate, signal_unit, rpm, fréquences de référence) : embarquer les mêmes clés dans nos captures `.spikypanda` ; convention JSON-metadata-à-côté-de-l'artefact pour nos bancs ONNX (introspection des params par un hôte).
- **`check_bearing_faults` accepte un dict `{label: hz}` arbitraire** : c'est le **point d'extension** où nos fréquences MCSA/broken-bar conditionnées au régime se branchent.
- **Manifest serveur MCP** compatible registre : `server.json` (`$schema` modelcontextprotocol, `name io.github.<org>/<repo>`, `registryType=npm`, transport `stdio` + sse/streamable-http).
- **Prompts guidés** (`diagnose_bearing`, `diagnose_gear`, `quick_diagnostic_report` en arbres de décision STEP 0..6) + fixture CI style `tool_inventory.json` qui valide chaque appel de prompt contre le registre live.

## 4. Notre avantage à GARDER (ne pas copier, ne pas remplacer)

- **Substrat appris** (LRU/SSM diagonal → biquads). Leur stack entier = scipy DSP + sklearn peu profond (17 features → PCA(0.95) → OneClassSVM/LOF), ré-entraîné par machine, **aucun filtre appris, aucun modèle de séquence**. Ne PAS remplacer notre substrat par leur DSP : **l'exposer comme backend supérieur qu'ils peuvent appeler**.
- **Streaming / on-sensor / temps réel à µW sur ESP32**. Chaque outil chez eux est batch, host-side, file-based. **Zéro** capacité streaming/online/on-device. C'est la couche qu'ils n'ont structurellement pas. Ajouter des handles `stream_id` (`open_stream`, `push_window`, `get_position`) avec la même discipline d'opaque-handle, mais **garder le moteur online chez nous**.
- **Régime-awareness** (RS-385) : fautes conditionnées au point de fonctionnement (BPFO suit un schedule, tolérance qui s'élargit en transitoire). Eux = rpm statique unique.
- **Open-set clustering + trajectoire** (POSITION drift boiling-frog + MotionWatch JUMP/FREEZE par composante). Leur anomalie = une frontière globale healthy-vs-not, sans mémoire temporelle ni décomposition par composante.
- **MCSA broken-rotor-bar validé ~88% on-sensor**. Étendre leur vocabulaire avec `broken_rotor_bar` plutôt qu'adopter leur check roulement mono-rpm comme détecteur.
- **Artefacts appris inspectables et portables** : exposer nos bancs comme `model_type` renvoyant des **coeffs biquad SOS** (portables MCU) + outillage déploiement qu'ils n'ont pas (`estimate_power_budget`, `target=esp32|browser`). Leur quartet pickle sklearn n'a **aucune story MCU**.
- **Déploiement browser ET MCU depuis un seul runtime TS, offline-first** (runtimes inline / SVG statique, pas de CDN). Leur design CDN-Plotly + pickle + Python host ne partage pas cet éthos.

## 5. Standards à citer (exactement, comme eux)

- **ISO 13374** : architecture en blocs du condition monitoring (1 Acquisition, 2 Manipulation, 3-4 State/Health, 5 Prognostic, 6 Advisory).
- **ISO 10816-3:2009** : les valeurs de la table 4-zones (A/B/C/D) RMS vitesse (mm/s).
- **ISO 20816-3:2022** : édition courante qui **supersede** 10816-3 et **fusionne A/B** ; à citer dans la provenance.
- Vocabulaire machine ISO 20816-3 : `machine_group{1(>300 kW), 2(15-300 kW)}` + `support_type{rigid, flexible}` ; **PAS** le `machine_class I-IV` non-standard (qu'ils ont supprimé). Plancher de scope 15 kW.
- **Randall & Antoni (2011)**, MSSP 25(2) 485-520, doi:10.1016/j.ymssp.2010.07.017 : les formules cinématiques BPFO/BPFI/BSF/FTF.
- **ISO 15:2017** : dimensions d'encombrement roulement **uniquement** (PAS la géométrie interne) ; ne jamais y attribuer des fréquences de faute (leur erreur supprimée).
- Datasets de référence cités par entrée : **CWRU** (6205 BPFO=3.5848x) et **XJTU-SY** run-to-failure (UER204).
- `signal_unit{g,m/s2,mm/s,m/s}` et bande d'évaluation ISO 10-1000 Hz (bord bas 2 Hz sous 600 rpm) comme métadonnées standard.
- Manifest MCP : `modelcontextprotocol server.schema.json`.
