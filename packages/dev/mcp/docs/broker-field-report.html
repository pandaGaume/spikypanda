Integration report · @cyanmycelium/mcp-broker 1.2.1

Publishing a browser to a broker slot

Notes from wiring a browser-hosted MCP server into a broker slot and reaching it from an external client. The path works. Getting there cost far more than it should have, and every wrong turn failed silently.

Packagesmcp-broker 1.2.1 · mcp-core 0.7.0 · mcp-broker-provider 0.1.1 TopologyBrowser provider → WS tunnel → broker → Streamable HTTP client PlatformWindows 11 · Node 22.20

What we were building

Context for the findings below.

A graph editor that runs entirely in the browser publishes itself as an MCP server so an agent can drive it: list the node catalogue, compose a graph, set node properties, step the simulation, read back a recorded window. The runtime has to stay in the page, because the view and its time-series plots need it locally. That makes the broker the only way out.

This is exactly the row in the mcp-core README that reads “MCP server inside a browser, exposed to the outside → mcp-core + mcp-broker-provider → MultiplexTransport”. We followed it, and that turned out to be the single most expensive decision of the integration.

What worked well

Worth saying first, because the rest of this document is problems.

  • The _broker introspection tools are what made diagnosis possible. providers_list and provider_status turned a black-box hang into a precise measurement. Without pendingCount we would still be guessing.
  • “What to import for what” answered our exact question in one row. Most libraries make you infer that table.
  • “Two readings that trip people up” pre-empted two mistakes we were actively making — bundling the broker as a dependency, and thinking it was required to write a server. Documentation that predicts the reader's error is rare.
  • The startup banner is excellent. Every endpoint, plus auth state spelled out as “trusted network only”. Security posture visible without reading config.
  • Keeping the tunnel out of mcp-core was the right call, and the README says why: topology, not protocol. Paying a breaking change in 0.5.0 for that principle is unusual and correct.
  • --help was fixed the same day it was reported, covering -h and --version too.

Silent failures

Ranked by how long each one cost us. Every item here produced a working-looking system that did nothing.

Silent · highest cost

Multiplex transport on a slot-scoped URL registers, reports healthy, and never answers

We used MultiplexTransport.create(slot, "ws://host:3000/provider/<slot>"). The socket opened. The broker registered the provider and refused a second one with 1008 "already connected". providers_list reported it as connected. Every client request then hung forever.

Multiplex wraps messages in a named envelope so one socket can carry several servers. A slot-scoped URL carries plain messages. The transport therefore registered correctly and silently dropped everything afterwards. The only visible trace was in the broker's own accounting:

{"name":"spikypanda","transport":"ws","connected":true,
 "clientCount":0,"sessionCount":1,"pendingCount":1}

connected: true with a permanently rising pendingCount is the signature. Switching to new DirectTransport(url) fixed it immediately, and 21 tools appeared on the first call.

Ask

Detect the mismatch and say so. A registration frame arriving on a slot-scoped path, or a plain frame arriving at a multiplex transport, is unambiguous and could close with a reason instead of going quiet. Failing that, a warning after the first unanswered request would have saved hours.

Silent

Every WebSocket path accepts the handshake, including ones that do not exist

All three of these opened cleanly against a running broker:

ws://localhost:3000/providers              → OPEN
ws://localhost:3000/provider               → OPEN
ws://localhost:3000/provider/demo-slot     → OPEN   (never configured)

A wrong provider URL therefore gives no signal at connect time. Combined with the finding above, a typo in the tunnel URL is indistinguishable from a working setup until a client times out.

Ask

Reject unknown paths at the handshake, or at minimum log the connection with the path and the shape the broker expects on it.

Silent · mcp-core

server.start() resolves even when the transport never connected

Our publish routine logged “published to broker slot” on a page where the WebSocket had failed outright. The console showed the failure one line earlier; start() reported success anyway. We shipped a false positive into our own logs and trusted it for two debugging rounds.

Ask

Either reject when the transport reports a connect failure, or document clearly that start() is not a connection guarantee so integrators add their own gate.

Silent

MultiplexTransport.isOpen read false on a tunnel the broker considered live

Observed against a broker that was actively refusing a second provider for that slot — so the tunnel was demonstrably up. We tried to build a health check on isOpen and had to remove it, because it would have rejected working setups.

Ask

Clarify what isOpen tracks on a shared socket, and expose something an integrator can trust for a readiness check.

Silent

Port already in use exits quietly; the client sees only CONNECTION_CLOSED

Because the broker both binds a port and serves an stdio bridge, a host that spawns it per MCP server entry produces a second instance that cannot bind. It exits, and the client reports Connection closed with no cause. We chased this for a full round before finding a stray broker process holding port 3000.

Ask

Catch EADDRINUSE and print the port, the holding process if resolvable, and the suggestion to attach rather than spawn. This one is cheap and would pay for itself immediately.

Operational friction

Nothing broken, but each one cost a cycle.

Friction

A reloaded browser page orphans its slot

Reloading the provider page leaves the previous registration in place. The new connection is refused with 1008 "Provider <name> is already connected", and clients then route to a socket nobody is on. We fixed our side by releasing the slot on pagehide, but a browser tab that crashes or is killed cannot do that.

Ask

Consider treating a new registration for an unresponsive slot as a takeover, or add a liveness check. At minimum, document that a browser provider must release explicitly, because reload is the normal development loop.

Friction

MCP_BROKER_STDIO_PROVIDER=<slot> creates a startup ordering dependency

Pinning the bridge to a provider slot means the connection fails whenever the provider is not up yet — which, for a browser provider, is every single time the host starts before the page is open. The error is accurate (Provider <slot> not connected) but the setup is unusable as a default.

Pointing the bridge at _broker instead solves it completely: that server is always present, and providers_list then tells you whether the real provider has arrived. We found this by reading dist/.

Ask

Document _broker as the recommended stdio target for hosts that start before their providers, with the two-entry pattern below.

Friction

Origin checks apply even when the broker serves the page itself

Once the broker was serving the studio from its own www mount, we assumed same-origin requests would pass. They do not — the browser still sends Origin, and the endpoint answers 403 invalid_origin. Reasonable behavior, genuinely surprising in that configuration.

Related: allowedOrigins works as a config key (array or {pattern, flags}), but it appears in neither the example config.json nor the configuration reference — only MCP_BROKER_ALLOWED_ORIGINS shows up, in --help.

Ask

Add allowedOrigins to the example config, and note that a www mount does not exempt the served origin.

Friction

www.open can only open the root

The broker serving the provider page is an elegant topology — one process, one origin, no ordering problem. But open is a boolean that launches /, and a real app usually lives at a sub-path. Ours opens a landing page that publishes nothing.

Ask

Let www.open take a path or URL. It turns a nice-to-have into the thing that removes the ordering dependency entirely.

Documentation gaps

Where we went looking and did not find, or found two answers.

Docs

Two provider paths across two READMEs

The broker documents providers connecting to ws://<host>/provider/<name>, and paths.provider defaults to /provider. The provider README's multiplex example uses ws://localhost:3000/providers, plural. Since every path accepts the handshake, neither reader gets corrected.

The transport table itself is correct and clear. The failure is that choosing the wrong row has no visible consequence.

Ask

Align the example URLs, and state the pairing as a rule: DirectTransport with /provider/<name>, MultiplexTransport with the shared base.

Docs

The _broker slot and its tools are undocumented

broker_info, providers_list and provider_status are the most useful things in the package for anyone integrating, and we found them by grepping dist/. _all is mentioned twice in the README, but only in the context of policy filtering, never as an addressable slot.

Worth clarifying too: _all aggregates upstream servers, prefixed as _broker-providers_list and so on. It does not surface the tools of connected provider slots, which is what we first assumed from the name.

Ask

Give _broker and _all a short section: what each exposes, what it does not, and when to point a client at either.

How the failure actually unfolded

A real sequence, because the order is the point: each step looked like progress.

  1. Followed the README row for a browser server and chose MultiplexTransport.

  2. Publish logged success. server.start() resolved. We believed it.

  3. First client hung on initialize. We assumed our hand-written client was wrong and discarded it.

  4. A raw HTTP probe hung too. We assumed a self-deadlock, since the same page was both provider and client.

  5. A probe from a second tab hung as well. The deadlock theory died. First real evidence of a product-side problem.

  6. provider_status reported pendingCount: 1. The request reached the tunnel and was waiting. This one measurement moved the fault decisively to our transport choice.

  7. Swapped to DirectTransport. 21 tools on the first call, and a full round trip: catalogue read, node created, property written and read back.

Five of those seven steps were spent forming and discarding wrong theories, because nothing in the stack said no. Step six worked because provider_status exists.

Configuration that ended up working

Offered as a candidate recipe, since the two-entry shape is not obvious.

One entry spawns the broker and bridges stdio to its own server, so it connects whether or not any provider is up. The second reaches the provider slot over HTTP and deliberately spawns nothing, which is what avoids the port collision described above.

{
  "mcpServers": {
    "broker": {
      "command": "npx",
      "args": ["-y", "@cyanmycelium/mcp-broker"],
      "env": { "MCP_BROKER_STDIO_PROVIDER": "_broker" }
    },
    "studio": {
      "type": "http",
      "url": "http://localhost:3000/studio/mcp"
    }
  }
}

Samples worth shipping

In the order we would have wanted them.

Browser provider, end to end

The case the transport table names, as runnable code: page publishes, broker relays, external client calls a tool. Correct transport, correct URL, release on unload. This one sample would have prevented every silent failure above.

Host configuration recipe

The two-entry pattern, with the reasoning: why the stdio entry targets _broker, and why the slot entry must not spawn a second process.

Provider lifecycle

Connect, register, release. What a browser must do on unload, and what happens to a slot when it does not.

Broker as application host

Serving the provider page from the broker's own www mount: one process, one origin, no ordering dependency. Including the origin allowlist that is still required.

The one-line summary

The architecture is sound and the introspection tools are genuinely good. What cost us the day is that this stack fails quietly: a wrong transport, a wrong path, a dead socket and an occupied port all present as a healthy system. Most of the asks above are one log line each.
